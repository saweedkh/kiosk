# پیشنهاد معماری پوز — تصمیم نهایی

این سند جمع‌بندی است: چه کار کنیم که مبلغ روی پوز بیاید، بدون اینکه دوباره حدس بزنیم.

اسناد وابسته:

- چک‌لیست سر دستگاه: [`POS_ONSITE_CHECKLIST.md`](POS_ONSITE_CHECKLIST.md)
- پروتکل و عیب‌یابی: [`POS_PROTOCOL_AND_TROUBLESHOOTING.md`](POS_PROTOCOL_AND_TROUBLESHOOTING.md)
- کلیدهای `.env`: [`.env.pos.example`](../.env.pos.example)

---

## پیشنهاد من (یک جمله)

**الان DLL را داخل لینوکس نبر.**  
دفعهٔ بعد اول پکت را با نرم‌افزار شرکت هم‌تراز کن (۳۰–۶۰ دقیقه، ابزارش آماده است).  
اگر بعد از مقایسهٔ HEX هنوز مبلغ نیامد، **بریج ویندوز + DLL رسمی** را بساز — آن مسیر تولیدِ مطمئن است.

سه گزینه را قاطی نکن. ترتیب اجباری است: **فاز ۱ → در صورت شکست فاز ۲.**

---

## چرا این ترتیب؟

واقعیت‌های همین پروژه:

| واقعیت | معنی |
|--------|------|
| Backend داخل Docker لینوکس است | Windows DLL آنجا load نمی‌شود |
| نرم‌افزار شرکت از همان کیوسک مبلغ را می‌آورد | شبکه و خود پوز سالم‌اند |
| اپ ما `connect` + `sendall` داشت، ۱–۲ دقیقه صبر، پوز خاموش | TCP رسیده؛ **پکت معتبر نبوده** یا session تداخل داشته |
| کد فعلی DLL را صدا نمی‌زند | تقلید پروتکل است، نه درایور رسمی |
| `POS_USE_BRIDGE` / `PAYMENT_GATEWAY_NAME=bridge` | پیاده‌سازی در `pos_bridge/` + `docs/POS_BRIDGE.md` |

پس دو مشکل جدا داریم:

1. **ارزان و محتمل:** فریم پکت ما ≠ فریم DLL (`dll_exact` در مقابل `00xxRQ0xx…`)
2. **گران و قطعی:** بعضی مدل/فرمور فقط همان چیزی را می‌فهمند که DLL می‌سازد (تگ `TL`/`R`، handshake، ترتیب خاص)

فاز ۱ مشکل ۱ را در یک بازدید حل می‌کند.  
اگر حل نشد، دیگر وقت تلف کردن روی حدس تگ نیست — فاز ۲.

---

## چیزی که نباید بکنیم

| ایده | چرا نه |
|------|--------|
| DLL را کنار پروژه در گیت بگذاریم | کد آن را لود نمی‌کند؛ هیچ اثری ندارد |
| DLL را داخل کانتینر لینوکس با `pythonnet`/Mono اجرا کنیم | شکننده، غیررسمی، روی خیلی از DLLهای PNA کار نمی‌کند |
| COM/سریال به کد اضافه کنیم | مسیر پرداخت همیشه TCP است؛ نرم‌افزار شرکت هم IP بوده |
| فقط `PAYMENT_GATEWAY_NAME=pos` و امید | بدون فریم درست همان باگ قبلی تکرار می‌شود |

## فاز ۱ — هم‌تراز کردن پکت (انجام بده، اول)

هدف: پکت اپ = پکت نرم‌افزار شرکت، بدون DLL.

### روی کیوسک

1. نرم‌افزار شرکت را **ببند**.
2. در `.env` (از `.env.pos.example`):

```env
PAYMENT_GATEWAY_NAME=pos
POS_TCP_HOST=<IP-واقعی>
POS_TCP_PORT=1362
POS_MESSAGE_FORMAT=pardakht_novin_official
POS_USE_SIMPLE_FORMAT=True
```

3. `docker compose up -d --force-recreate backend`
4. `./scripts/pos-preflight.sh <IP> 1362`  
   حکم باید `READY` باشد و ASCII شبیه `00xxRQ0xxPR00…`
5. `send_pos_payment 10000` — مبلغ باید روی پوز بیاید.

### اگر باز نیامد

همان مبلغ را با نرم‌افزار شرکت بفرست + Wireshark/`tcpdump` روی پورت `1362`.  
دو HEX را نگه دار:

- `ours.txt` از `pos_preflight`
- `vendor.txt` از capture

بعد builder را **عین vendor** می‌کنیم (نه حدس جدید). این هنوز فاز ۱ است، فقط دقیق‌تر.

### چه وقت فاز ۱ کافی است؟

اگر بعد از `pardakht_novin_official` + simple، یا بعد از کپی دقیق HEX وندور، مبلغ آمد.  
برای بیشتر دستگاه‌های PNA همین کافی است و لینوکسِ خالص می‌ماند.

## فاز ۲ — بریج ویندوز + DLL (اگر فاز ۱ تمام شد و شکست)

هدف: لینوکس دیگر پکت پوز نسازد. DLL رسمی همان کاری را بکند که نرم‌افزار شرکت می‌کند.

**پیاده‌سازی آماده است:** راهنمای کامل نصب و API → [`POS_BRIDGE.md`](POS_BRIDGE.md)  
کد سرویس ویندوز → [`pos_bridge/`](../pos_bridge/)  
گیت‌وی Django → `PAYMENT_GATEWAY_NAME=bridge` (`apps/payment/gateway/bridge.py`)

DLL این پروژه (`pna.pcpos.dll`) کلاس `Intek.PcPosLibrary.PCPOS` است با
`TestConnection` / `send_transaction` / رویداد `GetResponse(string)`.

### معماری

```text
[کیوسک UI / Next]
        │
        ▼
[Docker Linux: Django]
  POST http://WINDOWS_HOST:9000/pay
  { "amount": 10000, "order_number": "K-…" }
        │
        ▼
   [ویندوز همیشه روشن — همان کیوسک یا PC کنارش]
  pos_bridge (Python + pythonnet)
    → Load pna.pcpos.dll
    → TestConnection / send_transaction
        │
        ▼
[پوز TCP 1362]
```

لینوکس فقط JSON می‌فرستد. ساخت `PR`/`AM`/`RQ` کار DLL است.

### کجا ویندوز باشد؟

| چیدمان کیوسک | پیشنهاد |
|--------------|---------|
| ویندوز + Docker Desktop | بریج روی **همان ویندوز host**؛ backend به `host.docker.internal:9000` |
| لینوکس خالص | یک PC/مینی‌پی‌سی ویندوز روی همان LAN، یا VM ویندوز روی کیوسک |
| چند کیوسک، یک پوز | یک بریج، یک پوز؛ همزمان فقط یک تراکنش |

### امنیت و عملیات

- بریج فقط روی LAN داخلی listen کند، نه اینترنت؛ `BRIDGE_TOKEN` بگذار
- فایروال: فقط IP کیوسک به پورت ۹۰۰۰
- نرم‌افزار شرکت را در تولید ببند — فقط بریج به پوز وصل باشد
- DLL و لایسنس روی ماشین ویندوز بماند

## مقایسهٔ نهایی

| | فاز ۱: TCP خودمان | فاز ۲: بریج + DLL |
|--|-------------------|-------------------|
| وابستگی OS | لینوکس کافی است | ویندوز همیشه روشن لازم است |
| شباهت به نرم‌افزار شرکت | تقریبی | تقریباً عین همان |
| کار روی کیوسک فعلی | همین هفته، با اسکریپت‌های موجود | نیاز به نوشتن سرویس + API DLL |
| ریسک تکرار باگ «مبلغ نیامد» | اگر فریم فرق کند، بله | خیلی کمتر |
| نگهداری | یک کدبیس | دو پروسه (Django + Bridge) |

---

## تصمیم عملی برای تو

1. **این هفته / بازدید بعد:** فقط فاز ۱. ابزار و داک آماده‌اند. اول `READY` + `send_pos_payment`؛ اگر شکست، دو HEX بیاور.
2. **اگر HEX وندور با builder قابل کپی نبود، یا بعد از کپی دقیق باز هم پوز ساکت ماند:** فاز ۲ را شروع کن. آن موقع بهترین راه‌حلِ پایدار است، نه فاز ۱ِ بیشتر.
3. **از الان DLL را داخل Docker امتحان نکن.** وقت و اعصاب می‌سوزاند و به معماری کیوسک لینوکس نمی‌خورد.

## چک‌لیست تصمیم سر دستگاه (یک صفحه)

```text
send_pos_payment / سفارش واقعی
        │
        ▼
مبلغ روی پوز آمد؟ ──بله──► تمام؛ فاز ۱ کافی است
        │ خیر
        ▼
ASCII ما 00xxRQ دارد؟ ──خیر──► .env را official+simple کن، recreate، دوباره
        │ بله
        ▼
HEX ما == HEX نرم‌افزار شرکت؟ ──خیر──► builder را عین وندور کن
        │ بله
        ▼
باز هم مبلغ نیست ──► فاز ۲: بریج ویندوز + DLL
```

## کارهایی که قبل از فاز ۲ باید از شرکت/کیوسک جمع شود

اگر احتمال می‌دهی به بریج برسی، همان بازدید این‌ها را بردار:

- [ ] فایل DLL + نسخه
- [ ] داک یا نمونه C#/دلفی شرکت (نام متد، واحد مبلغ: ریال یا تومان)
- [ ] OS کیوسک: لینوکس خالص یا ویندوز+Docker
- [ ] آیا می‌شود یک سرویس ویندوز دائم روی همان دستگاه/شبکه داشت؟
- [ ] دو فایل HEX (ما / وندور) برای همان مبلغ

بدون API DLL، فاز ۲ را شروع نکن.
